# Layer 3 追溯表：方法论

## 为什么需要追溯表

Human Gate 的本质是**让审核者能独立验证映射结果**。没有追溯表时，审核者在闸门处只能看到：

> "摩洛哥 3 月总计 75,580 套，来源：2026年下单 sheet"

这是一个**信任声明**，不是**可验证的事实**。审核者无法判断：
- 这个数有没有漏掉某条订单
- 有没有重复计算
- 聚合逻辑（SUM vs AVG）是否正确

有了追溯表，闸门变成可操作的检查点：

> "摩洛哥 3 月总计 75,580 套 ← 来自源表行 9, 15, 22, 37...（共 42 条）。抽查行 9：MO2511128061S，QTY=300，加总验证 ✓"

审核者可以**不信任 LLM**，直接打开源文件跳到指定行号，自己算一遍。置信度从"信 LLM"变成"信自己的眼睛"。

## 追溯表的数据来源

追溯表不靠 LLM "回忆"或"推断"来源。所有来源坐标来自 Layer 1 的**展平脚本**：

| 数据 | 谁提供 | 何时 |
|------|--------|------|
| `_source_row`（原始行号） | `flatten_table.py`（脚本） | Layer 1 展平时自动注入 |
| 列含义（如 B=月份, G=QTY） | `元数据.yaml`（LLM 分类） | Layer 2 产出 |
| 聚合逻辑（GROUP BY / SUM） | LLM（分析展平 CSV） | Layer 3 映射时 |
| 源行号列表（如 "行14,58,91"） | LLM（汇总 `_source_row` 列） | Layer 3 映射时 |

**关键原则：事实由脚本保证，判断由 LLM 提供，审核由人执行。**

## 三种数据场景的追溯需求

### 直接迁移（1:1）

最简单。每个目标单元格对应一个源坐标，没有聚合歧义。

- 追溯列只需要：目标路径 + 源坐标 + 源值
- 审核方式：随机抽查 3-5 个单元格，跳转到源表行号核对
- Layer 3 生成方式：遍历映射关系，对每个 1:1 映射输出源坐标

### 数据聚合（N:1）

最需要追溯。一个汇总数背后可能涉及几十条明细，是出错的高发区。

- 追溯列需要：目标路径 + 汇总量 + 来源行数 + 源行号列表
- **源行号列表是核心**：审核者手动加总对的上就过，对不上就查
- Layer 3 生成方式：
  1. 展平 CSV 按聚合键（如 Country+Brand+Month）分组
  2. 对每组，收集 `_source_row` 值形成列表
  3. 输出："N 条" + "行A,行B,行C..."

### 数据清洗（带规则）

不仅有聚合，还有规范化变换。规则本身的合理性需要审核。

- 追溯列需要：目标路径 + 最终值 + 清洗规则 + 源值 + 中间值
- 额外需要**清洗决策记录**：每个有歧义的决策（如 Kiowa/KIOWA 是否合并）单独记录
- Layer 3 生成方式：
  1. 先按聚合场景生成源行号列表
  2. 再对每条记录标注应用的清洗规则
  3. 将不确定的决策单独列出供审核

## 追溯表在 Gate 中的位置

追溯表嵌入 `{name}_映射表.md` 的末尾，紧接在指标映射表之后。审核者先看"指标映射"了解整体结构，再看"追溯表"做抽查验证。

Gate 展示顺序：
1. Layer 1 摘要（展平结果）
2. Layer 2 摘要（列分类）
3. Layer 3 映射表（指标映射）
4. **Layer 3 追溯表**（源行号→目标单元格的可验证链路）
5. 待决策事项

## 追溯表的质量标准

- [ ] 每个有值的聚合单元格都列出了贡献的源行号
- [ ] 源行号列表中的行号在源表中确实存在且有数据
- [ ] 多源行单元格标注了"来源行数"
- [ ] 零值单元格标注了"(无源数据)"而非留空
- [ ] 清洗场景有独立的"清洗决策记录"
- [ ] 抽查建议明确告知审核者如何验证（选哪几行、加总对照什么）
